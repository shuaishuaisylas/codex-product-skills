# 现状 PRD 的内容与证据要求

按项目类型选择需要的内容。不要把库/SDK 写成有不存在页面的应用，也不要把数据库实现细节直接堆成“用户需求”。

## 来源与范围

项目、仓库 URL、固定提交或附件哈希、许可、研究日期、模块范围、源码清洁状态、研究方法（源码/文档/实跑）、运行环境。先说交付还原哪个版本；源码来自本地修改时不能暗示远端同提交完全相同。

## 产品概览与角色

一句话能力、用户与使用场景、输入到交付物的核心任务。区分作者明确描述与分析推断；不能从代码还原真实访谈、需求起因、产品经营数据或决定功能优先级。

权限角色由实际行为确认。例如“匿名可浏览、登录后可编辑”不能进一步推断为多租户管理员/成员体系；数据库存在 User 表也不证明支持注册。

## 功能地图与流程

围绕用户任务组织功能，给出页面/CLI/API 入口、前置条件、用户动作、系统处理、状态转移与结果。用 Mermaid 或简洁顺序步骤表达真正存在的主流程；没有证据的分支保留待确认。

## 功能需求 FR

每条独立、可核验的 FR 至少包括：

| 字段 | 要求 |
|---|---|
| 编号与名称 | 与 evidence.json 保持一致，例如 FR-001 |
| 用户行为 | 谁在什么前提下触发什么 |
| 输入与规则 | 必填、长度、格式、默认值、约束的真实行为 |
| 输出与状态 | 页面/JSON/CLI 输出、成功反馈、数据变化 |
| 异常/权限 | 无权限、无数据、无效输入、资源不存在等已研究分支 |
| 验收条件 | 由现有行为还原的 Given/When/Then，可运行则关联 RUN；不是新增目标 |
| 证据状态 | 五种状态之一，详见 evidence-format.md |
| 来源 | 证据 ID、固定源码链接、运行案例；只引用确实读过的范围 |

FR 不必一条覆盖整个模块；某些分支没跑时拆开需求或明确只验证了哪些条件，避免一个成功案例让全部边界自动变成已验证。

## 数据、权限与非功能边界

只写与产品行为相关的实体、字段、关系、状态、持久化规则与权限。区分界面提示、后端校验和数据库约束。日期/年份输入长度检查不能改写成“必须为合法年份”；页面隐藏按钮不等于后端授权。

性能、并发、可用性、安全承诺和成本目标只有现有文档或实测证据才列为已知；单次运行耗时不等于产品 SLA。未研究到的部署/外部依赖、真实用户体验保留未核验。

## 验证与未决事项

列出本次实际执行的流程、证据路径、失败与未运行项。测试通过只能覆盖实际断言，不把测试数量等同完整业务质量。引用 Q 编号，将新增设计与当前事实分开。

## 另外两份产物

`需求证据索引.md`：推荐表格列为 FR / 需求摘要 / 状态 / 源码或文档链接 / RUN / Q / 证据限制。与 JSON 为同一台账的两种表达；不维护相互矛盾的第二份事实。

`待确认与改进建议.md`：问题使用 Q 编号，写原因、关联 FR、解决它需要的证据；后半部分放可选建议，注明尚未实现。别把未知项都转成要向用户提问，能继续查源码或运行的问题优先自行核验。
